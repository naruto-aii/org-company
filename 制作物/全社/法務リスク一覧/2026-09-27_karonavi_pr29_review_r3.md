## 2. メールアドレス匿名化のエラー無視（前回 N5）

**直った。** `20260927180000_delete_own_account_service_role_only.sql` から、`begin … exception when others … end` のブロックが削除されています。
- `auth.identities` の削除や `auth.users` のメールアドレス書き換えに失敗すると、関数全体が止まり、同じトランザクションで行った削除も取り消されます。Edge Function は `{ok:false}` を返し、アプリはログアウトしません。

## 3. 順番変更の検証（トークンが先に消えないか、残り続けないか）

コード（`supabase/functions/_shared/apple_account.ts` の `deleteThenRevokeAccount`）の流れ：
1. `read_apple_refresh_token` でトークンをメモリに読み込みます。トークンが無ければ、Auth の管理APIで Apple ログインかどうかを調べます。
2. `delete_own_account(uuid)` を実行します。失敗したら `delete_failed` を返して終わります。この場合、Apple には通信せず、Vault も残ります。
3. トークンがあれば、Apple に解除を依頼します（revoke）。失敗したら `apple_revoke_failed`。トークンが無くて Apple ログインだった場合も同じフラグを立てます。
4. **解除の成否にかかわらず**、`delete_apple_refresh_token` で Vault の行を削除します。この削除の失敗はログに残すだけです。

- **トークンが先に消えて解除できなくなる問題：なし。** `delete_own_account` は Vault に触れません（関数本体に vault の処理がないことを確認）。また、トークンは削除の前にメモリに読み込んでいます。
- **解除に失敗したとき、トークンが残り続ける問題：通常はなし。** 解除に失敗しても、手順4で Vault の行は削除されます。残るのは手順4そのものが失敗したときだけです。PR本文によると、後から掃除する処理はありません。
- 残る注意点（どれも公表を止めるほどではありません）
  - (a) 手順4が失敗して行が残った場合、ポリシーの「残ることがあります」とは一致します。ただし、目的を終えた認証情報を期限なく持ち続けることになります（個人情報保護法22条は、不要になったデータを遅滞なく消去するよう努めることを求めています）。削除済みユーザー（`public.users.deleted_at` あり）に対応する `apple_refresh_token:<id>` の行を定期的に確認して手作業で消すなど、運用の手順を決めることを推奨します。ログにユーザーIDは出ないため、こうした照合の方法が必要です。
  - (b) 手順1の読み取りに失敗した場合（一時的な障害など）、トークンを保存していても解除は依頼されません。そのうえで、手順4でトークンは削除されます。Apple ログインだと判定できれば、利用者には手作業での解除が案内されます。判定も失敗すると案内も出ません。10章の「トークンを保存している場合に限り…依頼します」と厳密には一致しない、まれなケースです。記載するかどうかは任意です。
- **文面と実装の一致**
  - privacy.html 10章、7章(2)、account-deletion.html、回答案の Other Data Types（「削除完了後に削除、失敗したら行が残ることがある」「保存していなければ revoke しない」）は、上の流れと一致しています。
  - アプリの表示「Appleとの連携を自動では解除できませんでした…」は、トークンが無い場合にも出るので、この言い方で正確です。
  - xcprivacy は変わっていません（Other Data Types、App Functionality）。これで整合しています。

## 4. 氏名の記載が残っていないか

- privacy.html：利用者の氏名を取得する記載はありません。「氏名: 麹池成」は事業者欄、「氏名やメールアドレスは載せません」は公開食品の説明なので問題ありません。
- 回答案：「氏名は要求しない。Name は収集しない」に更新されています。xcprivacy に `NSPrivacyCollectedDataTypeName` はありません。Info.plist にも氏名関連の記載はありません。**残りはありません。**
- **ただし要確認（R2）：Google ログインの氏名・プロフィール画像。**
  - ネイティブの Google ログイン（`GoogleSignIn(...)`）はスコープを指定しておらず、既定のスコープで動きます。Google Sign-In の既定には profile が含まれるとされ、その場合は ID トークンに name・picture が入ります。
  - Supabase Auth は、ID トークンの情報を `auth.users.raw_user_meta_data` に保存する仕様とされています。
  - どちらも本件では確認していません（未確認）。
  - 実際に保存されていれば、Apple の「Collect」（端末外に送って保存）に当たります。その場合は、回答案の「Name は収集しない」と、ポリシー3章「アカウント識別子（…メールアドレス）」が実態と合いません。
  - 確認方法：Supabase の管理画面で、Google ユーザーの `raw_user_meta_data` を見ます。
  - 保存されていた場合の対応：Name（App Functionality）を申告し、3章に「Google から提供される氏名・プロフィール画像」を追加します。あるいは、スコープを email に絞るなどして、保存しないようにします。削除時には `raw_user_meta_data` を `{}` にしているので、削除の記載とは矛盾しません。
  - この件は今回の変更で生じたものではなく、以前からの論点です。
