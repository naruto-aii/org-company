## 5. PR #29（Sign in with Apple のトークン失効）

**判定: 条件付き合格**

### 動作（コードから読んだ内容）
1. iOS/macOS のネイティブ Apple ログインが成功した後、authorization code だけを Edge Function `store-apple-refresh-token` に送る（`lib/repositories/apple_refresh_token.dart:13-45`、`supabase_authentication_repository.dart` の loginWithApple）。この保存に失敗してもログインは取り消さない（debugPrint の文言は固定で、code は出さない）。
2. 関数は JWT を `/auth/v1/user` で検証し（`apple_account.ts:325-356`）、Apple の `/auth/token` で code を refresh token に交換して、Vault に `apple_refresh_token:<uid>` として保存する（`20260927170000_store_apple_refresh_tokens.sql:30-88`、実行権限は service_role だけ :129-142）。
3. 削除時、アプリは RPC を直接呼ばず、Edge Function `delete-account` を呼ぶ（`account_deletion_rpc.dart:15-49`）。関数は トークン読み出し → Apple `/auth/revoke` → 利用者の JWT で `delete_own_account` → Vault のトークン削除 の順に処理する（`apple_account.ts:451-494`）。
4. 関数がない（404）なら「利用できません」を表示し、それ以外の失敗は固定文言を表示する（`account_deletion_screen.dart:80-95`）。サーバーの応答本文は表示しない（テスト `test/account_deletion_screen_test.dart` の追加分）。

### 失敗したときの挙動（質問への回答）
| 失敗箇所 | 削除は続くか | 利用者に伝わるか | 根拠 |
|---|---|---|---|
| トークンがない（PR29 以前のログイン、Web/Android、交換失敗、secrets 未設定） | 続く | **伝わらない**（`apple token revoke skipped` がログに出るだけ） | `apple_account.ts:463-479` |
| Apple の revoke が失敗（4xx/5xx/タイムアウト10秒） | 続く | **伝わらない**（status と error code だけログに出る） | `:465-476, :244-262` |
| delete_own_account が失敗 | 止まる（`{ok:false}` 500 を返す）。**revoke は先に実行済み** | 固定文言「削除に失敗」 | `:481-486, :519-522` |
| Vault のトークン削除が失敗 | 削除は成功扱い | 伝わらない。トークンが Vault に残る | `:488-492` |
| 関数が未デプロイ | 削除されない | 「利用できません」ダイアログ | `account_deletion_rpc.dart:26-28, 40-41` |

→ 失効しなくても利用者には「削除できた」ように見える。README にも「失効に失敗しても削除は止めない」と明記されている（`supabase/functions/README.md:8-11`）。

### 秘密情報
- Apple の秘密鍵・Team ID・Key ID・Client ID はコードにない。Edge Function の secrets（`APPLE_TEAM_ID / APPLE_KEY_ID / APPLE_PRIVATE_KEY / APPLE_CLIENT_ID`）から読む（`apple_account.ts:9-14, 59-68`、`README.md:18-44`、`config.toml:386-392` には名前だけで値はない）。
- PR29 の差分全体（2296行）を `BEGIN PRIVATE KEY`／JWT 形式／service_role の値／パスワードで検索した。**実際の鍵やパスワードは見つからない**。テストの鍵は実行時に `crypto.subtle.generateKey` で作っている（`apple_account_test.ts:44-53`）。テストの値は `TEAMID1234` などのダミー。`docs/app-review/demo-account.md` はパスワードを「ASC に直接入力し、ここには書かない」としている（:5, :21）。
- ログ: 固定文言か、status と英数字64字以内に制限した Apple の error code だけ（`:160-169`）。code やトークンを含む文は `logWithoutSecrets` で抑止する（`:70-82`）。user_id・メールアドレスはログに出ない。アプリへの応答は `{ok}`/`{stored}` だけ（`:228-236`）。
- client secret の JWT は ES256 で有効期間150日。Apple の上限は約6か月なので範囲内（`:16`）。リクエストごとに作り直し、保存しない。

### 新たな指摘
- 必須（判断を含む）:
  - (M1) **失効が失敗またはスキップされたときの扱いを決めること**。案は、応答に `apple_revoked:false` を含めて画面で「設定 > Apple ID > Apple でサインイン から手動で解除してください」と案内する、または Apple ユーザーの削除時に SIWA を再度出して新しい authorization code を取り、その場で revoke する（PR29 以前にログインした人の救済にもなる）。現状のままでは実機確認④が失敗しても気づけない。
  - (M2) 本番の前提がそろわないと④は通らない: 170000 の適用 → secrets 4つの設定 → 関数2つのデプロイ → **その後に**アプリをログインし直す（トークンが保存されるのは PR29 版でログインした後だけ）。この順序を実機確認の手順に入れること。関数が未デプロイの状態で PR29 版のアプリを出すと、アカウント削除そのものができなくなる（「利用できません」表示）。
- 任意:
  - (a) delete_own_account が失敗したとき、revoke は済んでいる。Apple 連携は切れたがアカウントは残る。再試行すれば削除できる（トークンは無効なので revoke 失敗→削除に進む）。実害は小さいが、順序（削除→revoke）の検討余地はある。
  - (b) 170000 は delete_own_account を変えない。そのため RPC を直接呼ぶ旧版アプリで削除すると、Vault にトークンが残る（孤児）。定期的な掃除か、delete_own_account 側で Vault を削除するかを検討すること。
  - (c) store 関数は code の `sub` と Supabase 側の Apple identity を照合していない。自分の JWT で他人の code を保存する攻撃は、code を入手できないと成立しないので影響は小さい（Ldr 判断）。
  - (d) store の失敗は HTTP 200 の `{stored:false}` を返すため、監視は関数ログだけが頼り。
- 戻し方: `supabase/functions/README.md:56-74` のとおり。(1) revert するとアプリは RPC 直呼びに戻る、(2) `rollback/20260927170000_store_apple_refresh_tokens_down.sql` で RPC 3つと `apple_refresh_token:*` の Vault 行を削除、(3) 関数を削除、(4) 任意で secrets を unset。down は delete_own_account に触らない（独立しているので順序の制約はない）。
- 未確認: `deno test`／`flutter test` の実行、Apple の実エンドポイントとの疎通、Vault 拡張が本番で使えるか、functions.invoke が 404/500 のときに FunctionException になるか（supabase_flutter のバージョン依存）、削除後の `signOut()` がサーバーで session_not_found になってもローカルのセッションが消えるか（`app_controller.dart:399-409` ではローカルデータの消去が先に実行されるので、データは消える）。
